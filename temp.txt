## What this is

A real-time, backend-driven Connect Four (4 in a Row) game: two players compete over WebSockets; if no
opponent appears within 10 seconds, a minimax bot takes over. During PvP matches, either side can ask an
AI assistant (separate Python/FastAPI service) for grounded advice on the current position. Full
architecture, data model, sequence flows, and API contracts are documented exhaustively in
[README.md](README.md) — read it before starting any non-trivial task, since it is the single reference
document for this project and answers most "how should X work" questions already.

exist, use `bun test <path>`.

(Fastify), `apps/assistant` on port 8000 (FastAPI). Redis runs via Docker on 6379 (6380 for the test
instance); test Postgres runs on 5433.

## Architecture

Two backend services, one authority: **Fastify (`apps/server`) owns all live game state and is the only
writer to it.** FastAPI (`apps/assistant`) reads game state via an internal service-to-service call but
never writes it — it exists solely to narrate hints using an LLM.

```
apps/web (React)  ──Socket.io──►  apps/server (Fastify)  ──imports──►  packages/engine (pure TS, no I/O)
apps/web (React)  ──SSE/REST───►  apps/assistant (FastAPI)  ──calls───►  apps/server /internal/analyze
```

- **`packages/engine`** — pure game logic (bitboard representation, minimax + alpha-beta, threat
  analysis). Zero runtime dependencies, no I/O. Adding an import to it is a mistake. Exposes
  `createBoard`, `applyMove`, `isLegal`, `checkWin`, `isDraw`, `bestMove(board, depth)`, and
  `analyze(board, player)` (structured facts consumed by the assistant, never raw board access).
- **`packages/contracts`** — Zod schemas for every socket/HTTP payload; the single source of truth for
  wire shapes, validated on both ends.
- **`packages/types`** — types inferred from `contracts` schemas plus hand-written types with no runtime
  shape (event maps, engine result types). Never declares a parallel interface to a Zod schema.
- **`packages/ui`** — shared shadcn/Base UI React component library consumed by `apps/web` via
  `@workspace/ui`.
- **Redis** is the authoritative live-state store (game state, matchmaking queue, disconnect grace TTLs,
  leaderboard, pub/sub for hint notifications) — never process memory, which is what keeps the server
  stateless and horizontally scalable. **Postgres (Supabase)** is the durable store for finished games,
  moves, and hints.
- **Redis key ownership is strict and single-writer**: Fastify writes `game:*`, `queue:*`, `player:*`,
  `disconnect:*`, `leaderboard`; FastAPI writes `hint:*`, `chat:*` and only reads `game:*`. Never cross
  this boundary.
- **The LLM never decides a move.** The engine computes facts (best column, threats, score); the LLM only
  phrases them. Any prompt that asks the model what to play is a bug.
- **The client is never trusted.** Every move is validated server-side against Redis state (turn
  ownership, column legality, game status).

See [README.md](README.md) for the full architecture diagram, Redis key table, Postgres schema, sequence
flows for every feature (matchmaking, moves, disconnect/reconnect, move timers, hints, game end), and the
security model (JWT for player identity, separate shared secret for service-to-service calls).



# CLAUDE.md

Behavioral guidelines to reduce common LLM coding mistakes. Merge with project-specific instructions as needed.

**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

## 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

## 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

## 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

## 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

---

**These guidelines are working if:** fewer unnecessary changes in diffs, fewer rewrites due to overcomplication, and clarifying questions come before implementation rather than after mistakes.
